2. Click New Base, inspect list. Select desired type, then confirm the prefilled name at (275,594).
3. Return from location at (815,600). Inspect map, choose speed, and wait only until completion/confirmation.

## Research allocation primitive

ResearchScreen.show computes [CPU Pool, best available Jobs] followed by all available unfinished technologies sorted by localized technology name (English locale here). Newly completed research disappears, newly unlocked research enters alphabetical order: never reuse a technology's old row number after a completion. CPU Pool/Jobs remain the first two rows. If target is below the visible window, use the list scrollbar/down arrow after reading the frame; keyboard arrows can instead move a selected slider, so they are not a safe generic list-scroll command.

For a zero-allocation visible row, drag from the actual thumb near the left edge (roughly x55) to x525 at its slider y to assign maximum. The historical Personal Identification trajectory used (76,256)→(520,256). Drag must start inside the thumb: slider.handle_drag explicitly ignores starts outside the thumb. Zeroing an already full allocation therefore starts at the right thumb and drags left. Read displayed allocated CPU after each drag.

For danger-1 research, the slider can be much shorter than the whole list because native research.py sizes it according to safe CPU availability. Use its visible endpoints, not blindly x525. Maintain enough unrestricted CPU for maintenance where relevant; free CPU pool also earns jobs after paying maintenance/building. A completed technology removes its allocation, so sequential research does not need a zeroing step after completion.

Exit via (500,512), inspect any warning, select desired speed, then wait. On a completed-tech dialog inspect label, dismiss, and check whether speed was automatically paused. Do not batch repeated waits while a modal dialog is visible.

## Short advancement schedule for author recording

At maximum speed each quota update advances4 game hours. Native ordinary actions consume6 updates, i.e. up to1 game day if the map remains active. Selecting maximum speed itself may therefore already finish a short construction or research and show its dialog: read the next observation before issuing any wait.

With update_ms33, waits of33/66/100/300/500/1000/5000ms request1/2/4/10/16/31/152 updates. Thus5000ms is potentially25⅓ game days, not5 game seconds. For the1–5-tick easy build/equipment witnesses, choose speed and inspect first; usually no additional long wait is needed. For research, estimate remaining CPU-days / currently allocated CPU ×6 ticks, subtract progress already seen, then use a short batch bounded by the next expected event. Using private telemetry for this author-only estimate is permitted; translating it to recorded wait/click actions is still required. Never edit native progress.

When a stage is finished, pause via(393,42) before more navigation if staying on the map would otherwise consume exposure time. Be aware that closing a dialog or pressing Continue can itself spend6 active updates; author witness tick counts exclude GUI transitions. Prefer33–300ms waits near a completion, and300–1000ms batches only while substantial research remains and no modal dialog is visible.
